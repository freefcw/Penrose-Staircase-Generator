## 依赖特点

### ✅ 优点

1. **单向依赖**: 从UI层 → 渲染层 → 核心层 → 算法层,没有循环依赖
2. **依赖倒置**: 高层模块依赖抽象(`Canvas`接口),而非具体实现
3. **抽象隔离**: `Canvas`抽象隔离了具体图形库(`graphics.py`)
4. **无环依赖**: 使用`TYPE_CHECKING`避免运行时循环依赖

### ❌ 问题

1. **app.py承当了太多的依赖**
   - 依赖ui、rendering、core、export等多个模块
   - 成为"god object",职责过重

2. **缺少服务层**
   - 应用层直接调用底层模块
   - 没有业务逻辑服务层缓冲

3. **紧耦合风险**
   - app.py与各个模块紧密耦合
   - 修改一个模块可能影响app.py

## 依赖统计

```
模块名称              被依赖数   依赖其他模块数   稳定性
───────────────────────────────────────────────────────
pstairs.py              1           0          100% (最稳定)
core/staircase.py         5           1          83%
core/geometry.py          4           1          80%
core/theme.py             3           1          75%
rendering/canvas.py       3           2          60%
rendering/renderer.py     2           3          40%
ui/control_panel.py       1           2          33%
app.py                    0           6          0% (最不稳定)
```

*稳定性公式: 稳定性 = 被依赖数 / (被依赖数 + 依赖其他模块数)*

## 改进建议

### 当前架构
```
ui/ → app.py → rendering/ → core/ → pstairs.py
```

### 建议架构
```
ui/ → app.py → services/ → rendering/ → core/ → pstairs.py
                    ↓
              coordinator/ (业务协调)
```

1. **引入服务层**: 在app.py和底层模块之间添加服务层
2. **引入协调器**: 将协调逻辑从app.py移至独立的协调器
3. **依赖注入**: 使用DI容器管理依赖关系
4. **事件驱动**: 使用事件总线降低模块间直接依赖
